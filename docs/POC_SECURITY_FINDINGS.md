# Authority demonstration: security findings

## Audit remediation

The evidence-verification findings were reproduced with recomputed checksums.
The verifier now pins the expected raw error diagnostics, verifies actual ML-DSA
credentials and specific negative mutations, correlates replayed entries with
consumed successful credentials, verifies the issuer signature on the rejected
classic Payment and checks its post-lock interval. Historical negative responses
remain transcripts rather than signed attestations.

Schema v2 binds the tool version and source identity, explicit issuer configuration
and cryptographic mechanism. Every raw read ledger must fit the declared interval;
future timestamps fail and generator time is labelled untrusted. Changed authority
returns structured STALE paths; unavailable required live evidence returns
INCONCLUSIVE with no freshness claim. Only exact immutable historical assessments
may use the legacy schema. Archived inputs are checked by content hash.

The fresh registry adds `set_role_quorum_if_revision`. It rejects stale expected
revisions with error 15, without a state write or contract event. Every declaration
in the current PoC uses this guarded API; compatibility callers may still choose
the legacy unconditional setter. Two local regressions cover conflict rollback
and actual tenant authorization. Both assets also rejected a stale revision in
enforced Testnet simulation.

Twelve additional Python regressions cover the reported evidence defects, raw
diagnostic causes, missing tool metadata, schema downgrade, issuer/configuration
binding and structured unavailable-evidence results. Required baseline sources,
pinned dependencies and the retained public proof fixture form the reproducible
release snapshot. Final clean-checkout results and the repeated internal review
are recorded in `evidence/qasset-remediation-validation.json`.

## Scope and verification implementation

Only SAC `set_authorized` is admitted by the administrator. ML-DSA-65 is
verified inside Wasm with unaudited RustCrypto `ml-dsa` 0.1.1, using context
`qasset-sac-admin-auth-v1`. This build does not use CAP-87 host verification.

## Findings discovered during continuation

- The initial test fixture omitted `AUTH_REQUIRED`, so new holders were
  authorized before negative attempts. All ten failing state assertions were
  retained; the fixture now sets `AUTH_REQUIRED` as well as `AUTH_REVOCABLE`.
  This corrected a fixture assumption, not the contract's authorization logic.
- Testnet estimated 14,112,589,523 stroops for the first Wasm upload. SDK 14
  assembly put that value into a uint32 fee field and could not serialize it.
  The runner now uses a CAP-66 fee-bump envelope when necessary, preserving
  the full int64 resource fee. See `evidence/attempts/qasset-upload-simulation.json`
  and the offline fee-serialization regression. The protocol rule is described
  in [CAP-66](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0066.md#allow-resource-fees-to-exceed-uint32).
- The original constructor extended instance storage to the network's maximum
  TTL. A real deployment requested 350,522,103,378 stroops in resource fees
  and was rejected before inclusion for insufficient balance. The recorded
  candidate transaction hash is not an on-chain failed transaction. See
  `evidence/attempts/qasset-poc-max-lease.json`.
  Renewal now targets 120,960 ledgers (approximately seven days at five
  seconds per ledger), capped by the network maximum. Successful ML-DSA
  authentication renews the lease when below half that target. Operators
  must maintain storage availability; TTL expiration is not key rotation.
- Contract creation and ordinary issuer/registry calls require explicit
  source-account authorization entries. The runner records those entries,
  permits automatic filling only for source-account credentials, then runs
  enforced simulation before submission. Recording simulation alone is never
  used as evidence that a signature was accepted or rejected.

## Residual authority and limitations

The initially pending lock and live staleness branches were completed in a
new, explicitly approved run. The primary deployment now includes 28 successful
transactions, ten rejected simulations and one `txBAD_AUTH` submission
rejection. The original unlocked record is preserved separately. See
[`qasset-poc-staleness.json`](../evidence/qasset-poc-staleness.json) for the live
revision change and verifier exit code.

- Moving SAC administration does not remove the issuer's classic Payment
  or SetTrustLineFlags path. Locking an issuer is irreversible and is only
  permitted for an issuer generated by the same run with the exact environment
  gate enabled. A pending lock cannot establish restricted issuer authority.
- Transaction sources and fee payers still sign Ed25519 envelopes. Relays
  can submit an ML-DSA credential but cannot change its signed invocation.
- The fresh registry's registrar and tenant administrator are classical
  accounts. Registry quorums remain declarations, and `policy_assessment`
  remains `Unverified`. The guarded setter atomically checks the expected revision; the legacy unconditional setter remains available for existing callers.
- The administrator has no upgrade, key rotation, recovery, or outgoing SAC
  invocation entry point. Lost operator keys can make administration unavailable.
- Native tests do not measure metered Wasm cost. Live simulation and receipts
  supply that measurement. The earlier unlocked run's positive simulations declared
  102,504,931 and 102,501,961 instructions, with estimated resource fees of
  57,417 and 57,416 stroops. Storage fees are network-dependent. Bounded-lease
  admin deployment estimated 68,396,179 stroops for each instance in that run.
- An ordinary checksum is not a signed attestation. Simulation transcripts
  are recorded RPC responses, not ledger receipts or independent cryptographic
  attestations of historical rejection.
