# Compact recovery backend: next feasibility gate

2026-10-20. Read-only source investigation and public-fixture lossless compression measurement. No proof source edits, deployment or crypto security approval.

The measured leaf proof remains much too large. Its 8,893,905 bytes become 7,986,385 bytes with zlib9 or 7,767,592 bytes with XZ preset6: the latter still exceeds the recorded 132,096-byte **whole transaction** limit by 58.80 times, before envelope overhead. Input proof SHA256 is fdceefebfa4e6ec5a44f61faca25e06b7897f03869364704cb5c1e3bba818517. This tests ordinary lossless transport compression; it supplies no new proof or Soroban implementation. Exact bytes, encoding hashes, lossless round trips and pinned input hashes are recorded in [proof-transport-research.json](proof-transport-research.json); reproduce with `python3 scripts/check_proof_transport_research.py`.

## Existing candidates and concrete blockers

- **Current Plonky3 WHIR**: the inspected pin 4615dcda4ddc5f40ba471dca86352b893bf18f98 has `HidingWhirPcs`, explicitly an HVZK PCS, implementing `MultilinearPcs`. The current Q-Asset tool uses uni-stark's univariate `Pcs`, so WHIR cannot be substituted as one config parameter. The existing `multi-stark` backend accepts multilinear PCS but its whole protocol's sumcheck/zerocheck/lookup messages need a hiding argument too; a hiding commitment alone does not establish zero knowledge for those additional messages. Current WHIR ZK config comments also distinguish mask-query budgets from unresolved randomized-source/shared-challenge terms. Do not claim that its per-term target certifies end-to-end quantum knowledge security.
- **Plonky3 recursion** is an existing engineering route, not a demonstrated size solution. The current upstream README supports FRI/WHIR examples but says `--zk` requires FRI, defaults WHIR to 66 per-error-term bits, and warns that the unaudited code should not be used in production. ShorStop's pinned `docs/recursion-experiment.md` records an outer proving attempt killed above 16GB RAM, despite exploratory 16-query/zero-PoW outer parameters; no final recursive proof size was obtained. Removing hiding or lowering parameters to report a small outer proof would not solve the existing security requirement.
- **Binius/Iron Spartan** is a concrete isolated next comparator for the narrow leaf relation. ShorStop's frequently attractive 86,240-byte SHA512 row is explicitly a **non-ZK** argument. Its later ZK measurements use `ZKProver`/`ZKVerifier` and report time/RAM without a corresponding proof-size claim. The pinned adapter has an existing SHA512 gadget and fixes Binius64 at 115108d5a661d95c0b474b6ab02558bfe6c6bec7 through Cargo.lock. It proves a full digest, so our clamped-half relation and canonical action binding require a reviewed wrapper; exposing the full SHA512 digest unnecessarily reveals the nonce-prefix half and is a different disclosure boundary. No fitting ZK proof has been reproduced here.
- **Soundness Longfellow hidden-PK** provides an existing different secp256k1/Keccak relation, with author-reported 292,163-byte proof at default settings, already above the transaction cap. Its README's smaller settings reduce the cited classical security estimate; no SHA512 gadget was found in the inspected repository file inventory. It is not a ready Stellar Ed25519 seed backend.

## Chunking and aggregation

Uploading the current 8.9MB proof would require an absolute minimum of 68 transactions and 136 ledger entries under the recorded 132,096B transaction and 65,536B entry limits, ignoring all metadata/XDR overhead. These are lower bounds, not transaction estimates. The historical snapshot has CLI26/protocol29 compatibility limits and does not establish today's limits. An upload commitment authenticates bytes; it does not verify their proof relation. Uploading and then running an unchanged monolithic native verifier still requires a Soroban verifier port and measured execution/memory/cold-read limits.

Incremental verification is a separate verifier-state-machine project: transcript/statement/version binding, immutable chunk order/length/hash, bounded decoding, expiry/revocation checked at final use, invalid-session cleanup/rent and concurrent finalization must be specified. Only fully verified, current state may rotate authority. Offchain aggregation is useful only if the final onchain verifier checks the aggregate and each authorized recovery/leaf is bound; an operator's attestation substitutes a trust assumption.

## Recommended next gate

First reproduce a **genuine ZK Binius leaf comparator** from existing pinned code, with public fixture only, fixed SHA512/clamp relation and independently supplied public scalar, a canonically bound recovery digest, malicious wrong-witness proof rejection, separate verifier and exact proof bytes. Record the entire parameter configuration and obtain a defensible quantum knowledge/ZK assessment before claiming a security level. Enforce a bounded run and report setup/runtime failures. If that comparator does not fit comfortably below the transaction cap after actual transaction serialization, compare an existing hash-based recursive verifier route against a separately specified incremental verifier; both require a Soroban WASM cost probe before a Build-project delivery promise. No Go/No-Go may rely merely on PCS microbenchmarks or author proof-size claims for other relations.

## Lattice-proof and relation-reframing follow-up

[Compact backend lattice gate](COMPACT_BACKEND_LATTICE_GATE.md) started as literature review and now includes two new measured circuits. It checked an external Fiat-Shamir transcript-binding disclosure (OtterSec, 2026-03) against this project's pinned Binius64 commit by direct source inspection: the pinned revision already contains the exact reported fix text, so this project's Binius-based evidence is not built on the disclosed-vulnerable code path. It then built [`tools/binius-commit-prove-research`](../tools/binius-commit-prove-research) (SHA-256 preimage) and [`tools/binius-commit-prove-blake3-research`](../tools/binius-commit-prove-blake3-research) (BLAKE3 preimage, half the trace-length bucket), measuring both against the exact same pinned backend as the existing SHA-512+clamp+scalar-mult comparator: proof size barely moved even where the smaller circuit crossed a trace-padding bucket boundary (539,888 → 539,856 → 515,984 bytes) while prove/verify/setup time kept dropping (up to -52%) — see [binius-commit-prove-research.json](binius-commit-prove-research.json) and [binius-commit-prove-blake3-research.json](binius-commit-prove-blake3-research.json). The mechanism is now understood directly, not assumed: this backend's proof size scales with query-count times log(trace size), not trace size, so relation-shrinking alone cannot deliver the order-of-magnitude cut F-01 needs here — which redirects the next step toward a lattice-compression backend rather than implementing a novel algebraic hash gadget. That step was then attempted directly: LaBinius has no declared license anywhere in its repository and a hard, fallback-free AVX-512 dependency confirmed by a failed build on this evaluation machine (a dependency that would also block any `wasm32v1-none` port regardless of hardware) — it is now a closed, blocked candidate, not merely unevaluated. RoKoko, cloned and built separately, is Apache-2.0 licensed with a genuine portable fallback and measured a real 95-107 KB proof verifying in 0.39s with no SIMD at all, though that benchmarks its core argument machinery on a synthetic witness, not yet a wired hash-preimage relation. It also reads the canonical Binius64 specification (binius.xyz/spec.pdf) in full: the spec proves classical random-oracle-model soundness and knowledge-soundness explicitly, with quantified error terms, but its post-quantum claim is an unsupported one-line hedge repeated twice with zero QROM treatment in 55 pages — and it separately admits Binius64 verification "is not yet succinct," independent confirmation that the measured CPU cost is an upstream, acknowledged property, not a Soroban-port artifact. It also surveys 2026 lattice-based SNARK candidates (Module-SIS soundness) reporting sub-200KB proofs, unreproduced here. The transcript-binding check is resolved. A literature check (section 0c) then found a standing theorem (Chiesa-Manohar-Spooner 2019) that would close A-01 for Binius64's family if round-by-round soundness were shown for its LIOP — not yet shown, and a 2025 attempt to ease that requirement was withdrawn by its own author for a proof bug — plus a differently-shaped, more directly applicable standing theorem (Lai-Malavolta-Spooner 2022) for the lattice/Bulletproofs family RoKoko and LaBinius belong to. A-01 is now a precisely named, textually-confirmed gap with an identified (not yet satisfied) theorem and precondition, not merely "unestablished"; F-01's mechanism is understood. Section 0d then read the full text of all four papers (user-supplied, not fetched) and found both lattice papers' own proofs use only classical rewinding, never cite LMS22 despite shared authorship (Russell Lai), and that LMS22's theorem covers plain-SIS Bulletproofs only, not the vSIS commitment RoKoko and RoK and Roll actually use — narrowing the lattice-family task from "confirm an existing theorem applies" to "extend its framework to vSIS." Section 0e then read Håböck's BaseFold list-decoding-regime paper (IACR ePrint 2024/1571, user-supplied in full) and found it proves round-by-round soundness directly for FRI-Binius — the exact construction this project's own prior `BINIUS_SECURITY_REVIEW.md` already identified as Binius64's underlying PCS (same ePrint ID cited independently in both documents). This closes the specific open precondition §0c flagged on the Binius64 side of A-01; what remains is confirming Iron Spartan's sumcheck constraint-reduction layer composes with it under the standard round-by-round-soundness composition rule, then invoking CMS19 directly — a verification/assembly task against already-published proofs, not open research. Section 0f then checked this directly against the pinned Binius64 source and confirmed the favorable case: the mulcheck sumcheck completes fully with no oracle interaction (`crates/spartan-verifier/src/lib.rs:343-375`) before a separate BaseFold opening phase begins (`lib.rs:224-237`, backed by real FRI-Binius BaseFold, `lib.rs:280-301`) — clean sequential composition, not the harder interleaved pattern. Two narrow items remain (Libra-style ZK masking and BaseFold's ZK-hiding wrapper both preserving round-by-round soundness — standard, expected, not yet citation-confirmed), making A-01 for Binius64 a scoped verification task rather than open research. A further check against Justin Thaler's standard reference "Proofs, Arguments, and Zero-Knowledge" (downloaded and searched directly) independently confirmed round-by-round soundness for any sum-check-based protocol (citing Canetti et al.) and found the book's own discussion of the Libra-style masking-polynomial ZK technique Binius64 uses, stating it "plausibly preserv[es] post-quantum soundness" — an expert assessment, not a proof, but directly on point; only BaseFold's own ZK-hiding wrapper remains unaddressed by any source checked. F-01 on that same backend remains unsolved. A follow-up scoping pass on RoKoko found its "wire a real hash-preimage relation" task is substantial circuit-gadget engineering (its SNARK frontend is authors-labeled "EXPERIMENTAL" with no existing hash gadgets anywhere in the repository), not quick wiring as previously estimated. Every open item now has a specific owner (see section 5 of the lattice gate doc): Binius64's A-01 is ready for a scoped independent cryptographic review — the recommended next action — while both F-01 paths and the vSIS/RoKoko A-01 side are separately-scoped engineering/research work, not further unaided research by this project. The vSIS/RoKoko side of A-01 is unaffected by this and remains the more open of the two, while being the stronger side on F-01. A follow-up timing pass on Binius64's own pre-existing `tracing::info_span!` instrumentation (unmodified source, 8 native runs) then found F-01's actual hotspot by reading `crates/verifier/src/zk_config.rs:153-170` directly: the dominant cost (94-97% of wall time) is the real outer Spartan verification plus the actual BaseFold/FRI opening, run second and currently unspanned, not the structural IOP's bit-operation reduction phases measured in the cheap recording pass that runs first (3-5%, despite one of its sub-spans being named "PCS Opening") — see [verifier-profile-research.json](verifier-profile-research.json). F-01 remains open; this narrows the target for a reduction effort. A section-size breakdown of the 183,090-byte SDK wrapper against the 127,068-byte raw module then ruled out Cargo profile flags and avoidable `soroban-sdk` features as quick fixes for the 56,022-byte gap; both are already maximal, and the gap is inherent SDK contract-ABI glue — see [sdk-code-size-breakdown.json](sdk-code-size-breakdown.json). A follow-up pure-userspace sampling profile (`pprof`, no `sudo`) then decomposed that undecomposed step directly: roughly 71% of samples fall inside `binius_spartan_verifier::wiring`'s MLE-evaluation functions, not the BaseFold/FRI Merkle/hash machinery (under 5% combined) — see [verifier-wiring-hotspot-research.json](verifier-wiring-hotspot-research.json). This narrows the hotspot to function granularity without closing F-01, and no change was made to the pinned verifier. A fresh RoKoko clone (commit `c3f8206`) was then scoped directly against its own source for the F-01 RoKoko side, and tested against the live library rather than left as a reading exercise: a calibration test confirmed the documented binariness recipe accepts a malicious non-binary witness unless the caller separately checks the shipped value's own structure, and a further bisection found a more serious blocker — multiplying two independently-committed secret values (needed for every AND/XOR between different values) costs degree 4 and is rejected unconditionally, with or without weighting, because two different regions always need two distinct selectors. This is not resolved; see [ROKOKO_RELATION_WIRING_SCOPE.md](ROKOKO_RELATION_WIRING_SCOPE.md), updated same-day, for the full finding. F-01's RoKoko side is now blocked on this question, not merely "substantial engineering." A follow-up probe of the ring's internal structure then resolved this, not just found a lead: packing two secret bits into one ring element's two coefficients (confirmed, empirically and robustly across six varied inputs, to behave as a controllable quadratic-extension slot) and squaring that one region against itself yields `2*a*b` as a side effect, for free; tying this to a freshly committed `p_ab` region, and deriving XOR from the same packed value, both validated end to end -- honest witnesses accepted, two independently-malicious witnesses (wrong AND, wrong XOR) both correctly rejected. What remains genuinely open is not soundness (validated directly) but whether the sumcheck protocol underlying these claims is zero-knowledge-hiding, not merely sound -- a question this project cannot resolve by itself and now scopes for independent review, same as Binius64's own open A-01 question. A full 1-bit adder (sum and carry-out, needed six times per SHA-512 round) was then built from that same AND+XOR construction alone -- no digit decomposition, no shipped value -- and validated against all 8 input combinations plus six independently-malicious witnesses, each rejected. A scoped review request for the one remaining open question (zero-knowledge hiding, not soundness) is ready to send: [ROKOKO_ZK_HIDING_REVIEW_SCOPE.md](ROKOKO_ZK_HIDING_REVIEW_SCOPE.md). A separate, untested assumption in that scope document -- that rotation and carry-chaining get a "free" shift via a documented copy-claim recipe -- was then checked directly and found wrong (that recipe only ties same-index entries); what actually works, confirmed both accepting a correct shift and rejecting a corrupted one, is one individual length-1-region tie per shifted position, not one batched claim. See [ROKOKO_RELATION_WIRING_SCOPE.md](ROKOKO_RELATION_WIRING_SCOPE.md) for the full construction. **Correction, same day:** that AND/XOR gate and the full adder built on it were then found unsound -- their malicious tests only flipped the coefficient each gate gives meaning to, and an adversary putting junk in an ignored coefficient (with true AND = 0) was accepted by the live library while the gate read AND = 1. Both are superseded by a canonical design (every wire a pure scalar bit; primary inputs checked; gate outputs forced exact by the ties), which rejected that attack and now includes a 64-bit ripple-carry adder: 5 honest cases matching native `u64` addition accepted, 8 malicious witnesses rejected, 77 claims, ~80-210 ms prove, ~14-22 ms verify, front-end proof only. The same pass found the documented binariness recipe leaks the Hamming weight of secret bits through its shipped value, fixed with complement padding -- see [rokoko-canonical-gadget-research.json](rokoko-canonical-gadget-research.json).
